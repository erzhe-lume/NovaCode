# 第 15 章 长期团队（Team Lead 与队员并行协作）Spec

## 背景

主 Agent 目前只能串行/后台派发一次性子 Agent（第 13 章）或临时 worktree 隔离（第 14 章），
无法维持一批长期存在的队员并行干活、互相协作。本步把主 Agent 升级为 **Team Lead**：
创建长期团队、派生多个队员、队员通过共享任务清单和邮箱直接协作、干完空闲待命、
Lead 可在 coordinator 模式下专注调度。

## 目标

- 抽象长期存在的「小组」对象：记名称、负责人、成员花名册和持久化位置；成员记角色、
  工作目录、运行后端、是否需要审批。
- 支持两种成员运行后端：独立终端窗格里跑完整实例（强隔离），或同进程协程轻量跑；
  按环境优先级自动选，不静默降级。
- 给队员一组协作工具：共享任务增删查改（带依赖字段）+ 点对点发消息；主入口和普通
  子 Agent 看不到这些工具；需要审批的队员先发计划给 Lead，Lead 用结构化回复批准/驳回。
- 点对点消息走「名称注册表 + 邮箱文件」两段式；独立进程后端额外唤醒目标窗格；
  支持广播和几种结构化协议消息。
- Lead 把用户目标拆成带依赖的任务写进共享清单、派生成员；全部完成后用 git 合并各人
  目录，能解决冲突就解决，搞不定就回滚上报。
- 成员干完自然停下后标记空闲并通知 Lead；之后 Lead 发消息即可从磁盘恢复其上下文继续
  指派，不必重新 spawn。
- 独立 coordinator 开关：先在配置里开能力开关，再靠用户环境变量主动启用，两把锁都打开
  才生效；生效后剥夺发起方的写文件工具，保留读类工具和 shell（git 合并靠它），只留
  派人、终止、发消息、合并代码这些事。

## 功能需求

- F1（长期团队对象）：提供「小组」概念，含名称、负责人（Lead）、成员花名册、描述、
  创建时间与持久化位置。成员记录角色/Agent 类型、模型、工作目录（worktree）、运行后端
  类型、是否需要审批、是否在跑。团队与成员可落盘、可重建。
- F2（运行后端）：支持成员在独立终端窗格（tmux / iTerm2 分屏）跑完整实例做强隔离，
  或同进程虚拟线程轻量跑。按环境变量优先级自动选择后端（tmux 优先、其次 iTerm2、
  否则进程内），选择后不静默降级——后端不可用时显式报错，而不是悄悄换成进程内。
- F3（协作工具）：队员拥有共享任务清单的增删查改（含 `blocks` / `blocked_by` 依赖字段）
  和点对点发消息能力；主入口与普通（非队员）子 Agent 一律看不到这些工具。需要审批的
  队员先以只读身份产出计划发给 Lead，Lead 以结构化消息（携带请求 id 与 approve 字段）
  批准或驳回，批准前队员不能改文件。
- F4（消息机制）：点对点消息两段式投递——先经全局名称注册表把名字解析成投递标识，
  再写入目标成员邮箱文件。独立进程后端在投递后唤醒目标窗格。支持广播（发给同队其余
  成员）和结构化协议消息（关闭请求/关闭应答/计划审批请求/计划审批应答）。
- F5（Lead 编排）：Lead 把用户目标拆成带依赖的任务写进共享清单、派生成员并行执行；
  全部完成后用 git 把各成员目录（worktree 分支）合并回基线分支，可自动解决的冲突解决，
  搞不定的回滚并上报冲突文件。
- F6（空闲与恢复）：成员一轮干完自然停下后标记空闲并向 Lead 发空闲通知；Lead 后续发
  消息即可从已持久化的对话上下文继续指派，无需重新 spawn。
- F7（coordinator 开关）：双锁生效——配置文件能力开关为开 + 用户环境变量为开，两者
  同时满足才进入 coordinator 模式。生效后主 Agent 工具收窄为：只读工具 + shell +
  派人/终止/发消息/合并代码；写文件工具（建、改、删文件）被剥夺。

## 非功能需求

- N1（持久化）：小组配置、共享任务、成员邮箱均落到用户主目录下按小组名分出的文件夹；
  消息落盘自动补时间戳、默认未读。
- N2（并发安全）：邮箱文件用锁文件保护并发写；拿不到锁指数退避重试，锁文件过旧视为
  持有者已崩溃、可接管。
- N3（fail-closed）：关闭请求与审批应答的缺省判断一律偏向「不批准 / 不关闭」，
  避免静默误操作。
- N4（跨进程一致性）：共享任务读前重载磁盘；团队成员元信息可从磁盘重建。
- N5（上下文有界）：coordinator 指引全文只在首轮与每隔若干轮注入，其余轮用精简复述，
  避免占满 Lead 上下文。

## 不做的事

- 跨机器/跨主机的分布式团队。
- 成员之间的实时流式通信（每条消息随下一轮 prompt 注入）。
- 更复杂的任务依赖约束（拓扑排序、自动解锁、重排）。

## 验收标准

- AC1：建团队后磁盘出现按团队名分组的目录（config.json / tasks.json / inboxes/），
  重启后可按名恢复同一份团队与成员元信息。
- AC2：后端检测按环境优先级返回 tmux → iTerm2 → 进程内；后端不可用时报错而非静默降级。
- AC3：队员邮箱收发消息正常；消息带发送者、正文、时间戳、已读、摘要；未读即默认，
  已读可标记；并发写不丢消息；陈旧锁可被接管。
- AC4：共享任务清单增删查改与依赖字段生效，状态枚举合法；按状态/归属过滤可用。
- AC5：队员工具集含共享任务 + 发消息工具，不含 Agent / 建团队 / 删团队；主入口与普通
  子 Agent 不含任何协作工具。
- AC6：需要审批的队员先产出计划发审批请求，Lead 结构化批准后队员才拿到写权限；
  驳回则按反馈修订后重交。
- AC7：队员干完自然停下 → 空闲标记 + 通知 Lead；Lead 再发消息可从磁盘上下文续跑。
- AC8：改名注册表能按名字解析投递；广播一次送达全部其余成员；结构化消息带请求 id
  且应答能对回请求。
- AC9：git 合并可用——无冲突分支合并成功；有冲突自动回滚并报告冲突文件。
- AC10：coordinator 双锁未全开时不生效；全开后主 Agent 写文件工具不可见，只读 + shell
  + 调度工具可用。
