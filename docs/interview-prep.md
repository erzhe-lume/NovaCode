# 第二部分：面试题库（44 题）

> 答案都是第一人称口语化写法，基于真实实现，可以直接说。每题附可能的追问。

## A. 项目整体与技术选型

### A1. 为什么不用 LangChain / Spring AI 这些框架？
**答**：两个原因。第一，我的目的是理解 Agent 的底层机制——上下文管理、循环控制、工具调度这些最难的部分，框架恰好会帮你黑掉，用了框架我学到的就只有 API 拼接。第二，客观上 Java 生态的 Agent 框架也不够成熟，LangChain 主要在 Python 侧，手写反而完全可控。
**追问**：那你 Python 为什么不用？→ 答：我的技术栈和目标岗位是 Java，而且这个项目大量用到 JDK 21 的虚拟线程、sealed interface、模式匹配 switch，正好作为 Java 新特性的实战载体。

### A2. 这个项目的整体架构？为什么这么分层？
**答**：五层：交互层（Elm 架构 TUI）、引擎层（Agent Loop + 协议客户端）、工具层（注册表 + 7 个内置工具 + MCP）、记忆层（上下文压缩 + 跨会话记忆）、安全层（五层权限管道贯穿全层）。分层依据是变更频率和职责——后来加 MCP、Hook、Teams 的时候核心循环一行没改，验证了分层的有效性。

### A3. 为什么做终端 TUI 而不是 Web 界面？
**答**：三个理由：① Coding Agent 的使用场景本来就是开发者在终端里，Claude Code、Aider 都是这个形态；② 终端把并发模型和渲染解耦的问题暴露得很干净——Agent 跑在虚拟线程上，UI 只消费事件队列，这个解耦本身就是很好的练兵；③ 我用了 Elm 架构（Model/Message/Update 纯函数状态转移），比命令式渲染可控得多。

### A4. 项目里你觉得自己做得最好的设计决策是什么？
**答**：把系统提示拆成"字节级稳定前缀 + 易变后缀"。所有易变内容（环境信息、技能菜单、记忆索引）全部排在稳定模块之后，这个决策同时解决了缓存命中和 Plan Mode 提醒注入两个问题——提醒只在单轮请求期间插进历史，请求完立刻移除，不污染持久历史也不动前缀。

### A5. 如果重做一遍，你会改什么？
**答**：三件事。① 测试先行——测试套件是后半程才建的，前面靠冒烟脚本裸奔，有几次改动是靠运气没坏的；② Agent 类的策略配置一开始就该收敛成一个对象，我最初散了六组 volatile 字段，后来重构掉的；③ 事件协议一开始就该用 sealed interface，中途改的时候迁移了一批旧代码。
**加分句**：但这三个坑本身也有价值——我现在对"为什么测试要先行"的理解是踩出来的，不是背出来的。

### A6. 这个项目的代码规模和工作量？
**答**：1.3 万行 Java、25 个包、125 个源文件，205 个 JUnit 测试。从零包括：两套 LLM 协议的 SSE 解析、Elm 架构 TUI、五层权限、双层上下文压缩、MCP 客户端、Git Worktree 隔离、多 Agent 邮箱协作。断断续续迭代了多轮，每轮都是"改代码 → 跑测试 → 分析不足 → 修缺陷"的循环。

## B. Agent Loop 核心机制

### B1. 讲一下 ReAct 循环的工作流程？
**答**：用户输入一条任务，循环开始：每一轮把完整对话历史发给 LLM，模型要么返回纯文本（自然结束，任务完成），要么返回工具调用请求。有工具调用就执行——读文件、跑命令等——把结果作为 tool_result 消息追加回历史，进入下一轮让模型基于结果继续决策。直到模型不再请求工具，或者触发停止条件。

### B2. 循环怎么保证一定会停？有哪些停止条件？
**答**：四重。① 迭代上限（默认 50 轮，子 Agent 的角色定义可以用 maxTurns 覆盖）；② 连续多轮只请求到未注册的工具（说明模型在幻觉工具名），3 次熔断；③ 流超时 90 秒无事件视为请求失败；④ 用户随时 Ctrl+C/Esc 取消。另外每一处提前退出都要补齐历史尾部为 assistant 消息——否则历史以 tool_call 结尾、没有对应结果，下一轮请求 API 直接报错。

### B3. 取消正在执行的任务，怎么做到干净收尾？
**答**：Agent 跑在虚拟线程上，取消就是 interrupt。关键是三个位置的配合：循环顶部检查中断标志；事件队列 put/poll 处响应中断；工具执行线程池里的任务也会检查。收尾时把剩余未执行的工具调用全部填成"已取消"的 tool_result，保证 tool_call 和 result 成对，最后补 assistant 尾部消息。中间还有个细节：如果用户正卡在权限确认框，确认 future 要立即以"取消"完成，否则 agent 线程会一直阻塞在那里。

### B4. Agent 和 UI 之间怎么通信？
**答**：事件队列。Agent 循环只往 BlockingQueue 里 push 事件——流式文本增量、工具开始/结束、token 用量、权限确认请求、错误通知——UI 线程每 50ms poll 一次驱动渲染。好处是 Agent 和 UI 完全解耦，我测试的时候可以绕过 UI 直接消费同一个队列断言行为。

### B5. 工具调用失败会怎样？循环会崩吗？
**答**：不会。工具执行包了 try-catch，异常归一化成带 "Error: " 前缀的 tool_result 回流给模型——让模型自己看到错误、自己决定重试还是换方案，这比中断整个任务好得多。权限拒绝也是同样处理：拒绝原因作为 tool_result 回流，循环继续。只有流级别的错误（网络断、超时）才终止循环，而且现在有指数退避重试兜着。

### B6. Plan Mode 是什么？怎么实现的？
**答**：只读规划模式。实现在三个层面：工具 schema 按类别过滤只暴露只读工具（加一个任务清单工具，因为列计划本身就是规划的一部分）；每轮循环往历史里注入一条 system-reminder 提醒模型当前是规划模式、计划写到固定路径；关键细节是这条提醒请求完立刻从历史移除——不进持久历史、不动系统提示，稳定前缀字节不变，缓存不受影响。

## C. 上下文管理（最常被追问的主题）

### C1. 长会话上下文超限，你怎么处理？
**答**：两层防线。**预防层**：单条工具结果超过 8K token 就把全文落盘到本地文件，对话里只留 600 字符预览加文件路径——模型需要细节时自己用 ReadFile 读回来。批量场景还有一个合计阈值 16K，一批小结果加起来超了也按体积从大到小存盘。**兜底层**：整体估算逼近窗口上限时，用一个独立的、不配任何工具的 LLM 客户端把早期历史压缩成结构化摘要（固定五个板块：任务目标/已完成/关键决策/当前状态/待办），替换掉历史前段，只保留最近的对话。

### C2. 为什么不能简单地把历史截断？
**答**：三个致命问题。① 协议层面：assistant 消息带 tool_call 的话，对应的 tool_result 必须存在，截断位置不对 API 直接 400——所以我的压缩边界会强制对齐到非 TOOL 消息开头；② 信息层面：早期对话里可能有"用户否决过某方案"这种关键决策，截断后模型会重蹈覆辙，摘要能保留决策而截断不能；③ 缓存层面：任何对历史的修改都会使前缀缓存失效，所以压缩要尽量少发生——我把 DeepSeek 的窗口配置从保守的 64K 调到真实的 128K 就是这个目的。

### C3. token 数怎么估算的？为什么不用精确 tokenizer？
**答**：精确 tokenizer 要引入模型对应的词表依赖，而我发明了一个锚定式估算：每次 LLM 请求返回真实 usage 时，记录"当时的 token 数 + 当时的历史字符数"作为锚点；之后任意时刻的估算 = 锚点 token +（新增字符 ÷ 4）。误差被限制在两次请求之间的增量规模内，而不是整段历史的规模。这是个用 O(1) 成本换工程可用精度的典型权衡。

### C4. 摘要压缩本身失败了怎么办？
**答**：摘要也是一次 LLM 调用，可能失败。连续失败三次就熔断——不再尝试压缩，保证循环还能继续跑（超限了 API 会报错，但那是模型层的问题，不至于把本地循环搞挂）。压缩成功就复位计数。另外摘要用的客户端不配置任何工具，提示词里也双重禁止，杜绝模型在压缩时幻觉出工具调用。

### C5. 落盘的工具结果，模型怎么知道去读？
**答**：替换文本里带完整信息："[工具结果已存盘: .novacode/spill/tool_3.txt，共 45230 字符]" + 600 字符预览。模型看到感兴趣就自己发 ReadFile。压缩后的边界提醒里还会再提示一次："如需已存盘工具结果的完整细节，用 ReadFile 读取对应文件，不要凭摘要臆测。"

## D. Prompt 缓存

### D1. Prompt 缓存的原理是什么？你怎么设计的？
**答**：原理是前缀匹配——请求的前缀（tools + system + 消息开头）如果和缓存条目完全一致就命中，命中部分按一折计费。我的设计：① 系统提示拆成七个固定模块作为稳定前缀，所有易变内容排后面；② 对话历史只追加不修改；③ Anthropic 的显式缓存需要打 cache_control 标记，我打两个断点——system 上一个、最后一条消息的最后一个 block 上一个，这样上一轮写过的缓存这一轮自然命中，只在尾部增量续写。

### D2. Anthropic 和 DeepSeek 的缓存机制有什么区别？
**答**：Anthropic 是显式的——必须用 cache_control 标记，最长 5 分钟 TTL，有专门的缓存写价格（原价 1.25 倍）和读价格（0.1 倍）。DeepSeek 是自动的——无需标记，服务端自动做前缀匹配，无 TTL 声明。落地上的关键差异：DeepSeek 因为是自动前缀匹配，**对"历史被修改"极其敏感**——压缩重写历史等于全部缓存作废，所以适配 DeepSeek 的核心不是加开关而是减少压缩频率（窗口配到真实 128K）。另外 usage 统计口径也不同：OpenAI 系的 prompt_tokens 已包含命中部分，命中率算 hit/prompt；Anthropic 的 input_tokens 不含缓存，要算 read/(input+read+write)。

### D3. 缓存效果怎么验证的？
**答**：两个途径。一是状态栏实时显示命中率（协议感知的算法），实测长会话 57%；二是每轮循环的真实 usage 里解析 cache_read/cache_write 字段累计。有个踩坑：OpenAI 系开了 stream_options.include_usage 之后，usage 在一个 choices 为空数组的收尾块里，我原来的解析代码遇到空 choices 提前 return，把整次统计丢了——这也是测试抓出来的。

### D4. 为什么稳定前缀必须是"字节级"一致？
**答**：因为缓存匹配是字节级的，哪怕多一个空格、换个引号风格就整段 miss。所以我的 PromptBuilder 用确定性排序组装，环境检测这种内容放在前缀之外；连 Plan Mode 的轮次提醒这种每轮都变的东西，都设计成"插进历史、用完移除"而不是拼进系统提示。

## E. 并发与 Java 基础

### E1. 虚拟线程用在哪？为什么用？
**答**：两处。① Agent 循环整体跑在一个虚拟线程上——它 90% 时间阻塞在等 LLM 流式响应，是典型 IO 密集；② 一批并发工具调用的执行用 `Executors.newVirtualThreadPerTaskExecutor()`，每个任务一个虚拟线程。选择理由：工具执行（读文件、跑命令）都是阻塞 IO，平台线程池会白白占着线程等 IO，虚拟线程挂起零成本；而且这些任务没有 CPU 并行的需求，不需要池化复用。

### E2. 为什么 READ 工具并发、WRITE/COMMAND 串行？
**答**：按副作用分类。READ（读文件、搜索）是幂等的，并发不改变系统状态，并行只会更快；WRITE 和 COMMAND 有副作用，并发执行顺序不可控——比如模型同时请求"改文件 A"和"跑测试"，跑测试如果先执行，测的是改之前的状态，模型会被结果误导。所以执行器把连续的 READ 调用凑成一个并发批次，遇到写或命令就串行等待。权限前置检查故意放在并发路径之外，避免并发调用权限引擎。

### E3. 虚拟线程有什么坑？
**答**：我实际踩过的：① 虚拟线程不能被池化——per-task 建一次用完即弃，和传统线程池心智不同；② 阻塞在 synchronized 块上时会钉住载体平台线程（pinning），JDK 21 还没完全解决，所以共享缓冲区的短临界区我控制得很小，或者用显式锁；③ 调试时 jstack 默认不 dump 虚拟线程栈，排查要加参数。

### E4. 超时杀进程的坑，展开讲讲？
**答**：Bash 工具执行命令超时后，我最初只 `destroyForcibly()` 杀 cmd.exe 本身——结果测试发现命令的子进程（比如 ping）还活着，继续跑了几十秒占着工作目录。Windows 上 `cmd /c` 启动的是一个进程树，杀父进程不杀子孙。正确做法是 `process.descendants().forEach(ProcessHandle::destroyForcibly)` 先杀整棵树再杀父。这个是测试抓出来的——测试断言临时目录能被清理，孤儿进程占着就失败了。

### E5. 项目里遇到过什么并发 bug？
**答**：最近一个是超时判定的毫秒级竞态：子 Agent 排空循环里，poll 等待时长用 `deadline - now` 毫秒整数截断，导致 poll 会在 deadline 前零点几毫秒提前返回 null，代码随即判定"队列静默"硬失败——本该进入可续跑的 Detached 状态却直接报失败。修法是有 deadline 时 poll 提前返回就 continue 继续等，到点了才判定。这个 bug 平时完全无感，是写边界测试才暴露的。

### E6. BlockingQueue 在项目里怎么用的？
**答**：三处。① Agent 循环 → UI 的事件管道（LinkedBlockingQueue，容量 64，put 阻塞天然做背压）；② 协议客户端 → Agent 的流式事件（SSE 解析线程往里放，循环线程 poll 90 秒超时）；③ 权限确认用 CompletableFuture 而不是队列——因为需要的是"一次请求一次应答"且要拿到返回值，future.get() 可被中断的特性还正好支持取消。

## F. 权限与安全

### F1. 让 AI 执行 shell 命令，安全怎么设计？
**答**：五层管道，按顺序短路，deny 恒优先：① 命令黑名单（rm -rf /、dd 写块设备、fork 炸弹、Windows 整盘 del/rd/Remove-Item、format 等模式匹配）；② 路径沙箱（文件工具的路径必须解析在项目根内，`../` 逃逸直接拒）；③ 三级规则引擎（用户本地 > 项目 > 全局，同层 deny 压过 allow，近层优先）；④ 权限模式兜底（default 只放行只读 / acceptEdits 放行写 / plan 只读 / bypass 全放，黑名单沙箱仍然生效）；⑤ 人在回路确认——落到 Ask 就弹确认框，用户可以允许一次、永久允许（写入本地规则）、拒绝或取消。

### F2. 子 Agent 的权限和主 Agent 一样吗？
**答**：不一样，这是刻意设计。子 Agent 没有人在回路——它的确认请求没有 UI 可以弹，所以权限引擎构造时 prompter 传 null，任何落到 Ask 的调用直接降级为 Deny（安全默认），但黑名单、沙箱、显式规则仍然全部生效。子 Agent 委派出去的任务只能做"当前模式本来就允许"的事。我测试里验证过：DEFAULT 模式的子 Agent 写文件会被拒，ACCEPT_EDITS 模式的子 Agent 写文件直接放行——模式正确传递、无 HITL 降级两条语义都成立。

### F3. AI 的输出直接渲染到终端，有什么风险？
**答**：ANSI 注入——模型（或它读到的恶意网页内容）输出转义序列可以清屏、改标题、伪造界面。我的防御是渲染前统一 sanitize：剥离所有 CSI/OSC 转义序列，保留 tab 和换行，其他 C0 控制字符全部丢弃。这里我自己踩过一个深坑：解析 CSI 序列时判断终结符的循环从 intro 字符开始扫，而 `[` 恰好在终结符 ASCII 范围内（0x40-0x7E），导致序列被立即"终结"、后面的恶意字节漏进终端——防御形同虚设。这个 bug 是补测试时发现的，修复方式是扫描从序列体开始。

### F4. "读后才能改"是怎么强制的？
**答**：FileStateCache。ReadFile 时记录路径+mtime，EditFile/WriteFile 已有文件时校验：没读过直接拒，错误信息指引先 Read；后来我加了 mtime 比对——文件读过之后被外部（Bash 命令、编辑器）改过的话，缓存的视图就过期了，基于过期内容编辑会静默覆盖别人的修改，所以 mtime 变了也拒，要求重读。工具自己写完会 update 刷新 mtime。这也是测试抓出来的：最初版本只查"读过没有"，根本不比对时间戳。

### F5. 永久允许一条规则，怎么防止它被滥用？
**答**：ALLOW_FOREVER 写入的是项目本地配置文件（.novacode/permissions.local.yaml），规则格式是"工具名+路径通配"，只对完全匹配的 subject 生效，glob 元字符做了转义防注入。用户随时可以 /permission 查看全部已加载规则和来源层级。

## G. 协议与网络

### G1. SSE 流式响应怎么解析的？遇到过什么问题？
**答**：手写的。SSE 格式是 `event: xxx\ndata: {...}` 空行分隔，我逐行读、按空行分帧、Jackson 解析。难点在状态累积：tool_call 的 JSON 参数是分片下发的（input_json_delta / arguments 增量），要按 index 累积到 StringBuilder，块结束时整体反序列化。踩过的问题：① OpenAI 系的 usage 统计在 choices 为空数组的收尾块里，解析器遇到空 choices 提前 return 会丢统计——把 usage 解析挪到 choices 守卫之前；② Anthropic 的 thinking 块和 text 块共用 content_block_delta 事件类型，要按块类型区分路由。

### G2. 网络抖动、限流怎么处理？
**答**：协议客户端层做了指数退避重试：408/429/529/5xx 和连接失败按 1s→2s→4s 退避，最多 3 次。判定很保守——4xx 参数错误、鉴权失败这些不可重试的错误绝不重试，避免放大问题。重试前会把上一次的错误响应体排干再复用请求。这解决的问题是：Agent 跑几十轮的任务，不该被一次瞬态 429 打断。

### G3. 中文 Windows 下你遇到什么编码问题？怎么系统性解决的？
**答**：两层。文件层：中文 Windows 上大量 GBK 编码的历史文件，按 UTF-8 读会乱码或报错，我做了探测式解码——严格 UTF-8 解码失败就降级 GBK；关键是 EditFile 写回时要用探测到的同一编码 + 保留 BOM，否则 GBK 文件编辑一次就被静默转码成 UTF-8，git diff 全文件爆炸。进程输出层：cmd.exe 输出是 GBK，同一套探测逻辑复用。TUI 层最隐蔽：JVM 输出 UTF-8 而控制台代码页是 GBK(936)，界面整体乱码像"没渲染"——启动脚本 chcp 65001 切 UTF-8 加 JVM stdout.encoding 参数双保险。

### G4. 消息历史发 API 前要做什么处理？
**答**：两个关键点。① 协议格式转换：内部统一的消息模型（user/assistant/tool 三种角色）转成 Anthropic 的 content block 数组格式，其中连续的工具结果必须合并成一条 user 消息里的多个 tool_result block——逐条拆成多条 user 消息违反 API 规范，严格校验的 provider 会 400。② 缓存断点打在最后一条消息的末尾 block 上，实现增量缓存。

## H. 测试与工程质量

### H1. 205 个测试怎么组织的？重点测什么？
**答**：JUnit 5，按包对应被测类。最有价值的一类是 **AgentLoopTest**：用脚本化的 FakeClient 实现 LlmClient 接口，按剧本回放响应（第一轮返回工具调用、第二轮返回文本），驱动真实的 Agent 循环跑端到端——验证自然停止、工具结果回流进下一轮请求、权限拒绝回流、迭代上限、plan mode 工具收窄、hook 注入与清理、并发批次配平。这类测试不 mock 循环本身，mock 的是循环的外部依赖（LLM），所以测的是真实行为。

### H2. 测试抓出过什么 bug？举一个印象最深的。
**答**：ANSI 注入防御失效。我原以为 sanitize 函数是对的——逻辑上看确实在剥离转义序列。写测试逐字符断言才发现：CSI 序列的终结符 ASCII 范围是 0x40-0x7E，而序列的 intro 字符 `[` 是 0x5B，恰好落在终结符范围内——扫描循环把 intro 当成了终结符，每个序列都被提前一字符"终结"，后面的字节全部漏进终端。修复是扫描从序列体开始。这个 bug 的教训是：安全函数"看起来对"没有任何意义，必须逐字符行为断言。

### H3. 测试遇到过 flaky 吗？怎么处理的？
**答**：遇到几类，全部修掉了。① NTFS mtime 粒度约 10 毫秒，连续两次写文件 mtime 可能相同，"写入后应拒绝"的断言就看运气——改成显式 setLastModifiedTime 确定化；② 会话 ID 是秒级时间戳+随机后缀，同一秒创建的两个会话按 ID 排序不稳定——测试里 sleep 超过 1 秒，或者断言改成按动态获取的 ID 而不是硬编码；③ 异步回调竞速——自然停止回调在循环结束事件之后才触发，测试立刻断言就赛跑——用 CountDownLatch 等回调完成。修完后整套测试连跑三遍全绿。

### H4. 测试怎么隔离环境的？
**答**：三类隔离。① 文件系统：所有落盘测试用 JUnit 的 @TempDir，并把 user.dir / user.home 系统属性在 @BeforeAll 重定向、@AfterAll 恢复——因为任务清单、会话存档、团队目录都是从这些属性解析路径的；② 网络：协议层测试只测消息构建和 SSE 解析这些纯函数，不发真实请求；③ LLM：FakeClient 脚本化回放。原则是单元测试绝不依赖外部服务和真实密钥。

### H5. 有 CI 吗？
**答**：GitHub Actions，push 触发，Windows runner 上 JDK 21 跑全套测试加打包。选 Windows runner 是因为测试里有平台相关断言（cmd 行为、GBK 编码、进程树），和开发环境一致。诚实地说 CI 现在还在完善中——GitHub 的 workflow 文件推送需要专门的 token 权限，我刚配到一半。

## I. 开放反思题

### I1. 这个项目最难的 bug 是什么？
**答**（推荐讲编码这个，最立体）：中文 Windows 的 TUI 整体乱码到像"没渲染"。难在定位而不是修复——我自己的开发环境和用户环境有个关键差异：我派生的子进程没有真实控制台，JLine 会降级到 dumb terminal，永远无法复现用户看到的画面。最后用逐层排除法（日志里有无 dumb 警告区分两条路径）锁定了差异，再用屏幕截图在真实控制台验证修复。学到的通用教训：**环境差异本身就是 bug 的一半**，排查前先确认"我复现的是用户的环境吗"。

### I2. 如果要上生产，这个项目还缺什么？
**答**：我会主动列四点，展示我知道边界在哪：① 评估体系——现在只有单元测试保证"行为不变"，没有任务成功率评测保证"效果变好"，这是玩具和产品最大的分水岭；② 可观测性——需要结构化的 trace（每轮的 prompt/响应/工具调用全记录）而不是现在的文本日志；③ 沙箱强度——路径沙箱挡得住文件逃逸，挡不住命令本身的网络访问，生产要容器化；④ 多平台——目前编码处理是中文 Windows 特化的。

### I3. 你从这个项目学到的最重要的一件事？
**答**：**Agent 的质量上限不由框架决定，由上下文管理决定。** 模型能力是外部给定的，我的代码能做的是把对的信息在对的时候放进窗口——工具结果怎么截、摘要怎么写、缓存前缀怎么保、失败怎么回流。这个认知反过来让我看任何 Agent 产品都能快速判断它的功力在哪。

### I4. 下一步打算怎么发展这个项目？
**答**：两个方向，优先级明确。短期是"用起来"——拿它干真实的开发任务，收集真实使用里的摩擦点，这比再堆功能有价值；中期想补一个微型评测：选十个真实小任务写脚本批量跑、统计成功率，因为"如何测量 Agent 质量"是这个领域真正的稀缺技能。功能层面反而克制——架构上欠的重构已经还完了，剩下的候选都有意压着。
